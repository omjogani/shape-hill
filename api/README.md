# shapehill api

Go API with Postgres 17. Schema is managed declaratively with [Atlas](https://atlasgo.io):
you edit `schema.sql`, Atlas generates the migration.

## Setup

```bash
cp .env.example .env      # local defaults work as-is
docker compose up -d      # Postgres 17 on localhost:5432
go run .
```

## Layout

| Path | What |
| --- | --- |
| `schema.sql` | Source of truth for the `public` schema — **edit this**, not the migrations |
| `migrations/` | Generated by Atlas. Committed. Never hand-edit |
| `atlas.hcl` | Two envs: `local` (Docker) and `supabase` |
| `config.yaml` | Non-secret defaults (port, log level) |
| `.env` | Secrets — gitignored |

## Database

```bash
docker compose up -d              # start
docker compose down               # stop, keep data
docker compose down -v            # stop, wipe data
docker compose logs -f postgres   # tail logs

psql postgres://postgres:postgres@localhost:5432/shapehill
```

Connection string (already in `.env.example`):

```
postgres://postgres:postgres@localhost:5432/shapehill?search_path=public&sslmode=disable
```

## Migrations

Never hand-write a migration. Edit `schema.sql`, and let Atlas diff it.
Atlas needs Docker running — it spins up a throwaway Postgres to compute the diff.

### 1. Generate

```bash
atlas migrate diff --env local "add_users"    # writes migrations/<ts>_add_users.sql
```

Read the generated SQL before going further. If it's wrong, delete the file,
fix `schema.sql`, and re-run — don't patch the migration by hand.

### 2. Push to local

```bash
atlas migrate apply --env local --dry-run     # print the SQL, execute nothing
atlas migrate apply --env local               # push it
atlas migrate status --env local              # applied vs pending
```

### 3. Push to Supabase

Set `SUPABASE_DATABASE_URL` in `.env`. Atlas does **not** read `.env` (only the Go
app does) — it reads the shell environment, so export it first:

```bash
set -a; source .env; set +a

atlas migrate status  --env supabase          # what's pending there
atlas migrate apply   --env supabase --dry-run
atlas migrate apply   --env supabase
```

Each Atlas env has its own variable — `local` is pinned to the Docker container in
`atlas.hcl`, `supabase` reads `SUPABASE_DATABASE_URL`. Nothing you put in
`DATABASE_URL` can reach Supabase, and vice versa.

Apply is transactional per file (`--tx-mode file`), so a failing migration rolls
itself back and leaves the schema untouched.

### Rolling back

```bash
atlas migrate down --env local --dry-run                  # preview the revert
atlas migrate down --env local                            # revert the last migration
atlas migrate down --env local --to-version 20260101000000  # revert down to a version
```

Reverting a migration does not touch `schema.sql` — edit it back too, or the next
`diff` will just re-add what you dropped.

### Other

```bash
atlas schema inspect  --env local     # dump the live schema
atlas migrate validate --env local    # check migration dir integrity (atlas.sum)
atlas migrate hash                    # re-hash after resolving a merge conflict
```

### Supabase notes

`SUPABASE_DATABASE_URL` is the **direct connection** from
Project Settings → Database → Connection string → URI.

It must be port **5432**. The pooler on **6543** uses transaction-mode pooling,
which breaks DDL and advisory locks, so migrations will fail against it.

Atlas is scoped to the `public` schema via `search_path`, so Supabase's own
`auth` / `storage` / `extensions` schemas are left alone.

If the Supabase database already has tables that predate these migrations, the
first apply will refuse to run against a non-empty schema. Baseline it once:

```bash
atlas migrate apply --env supabase --baseline 20260101000000
```

### Notes

- The `local` env is safe to apply to — its URL is hardcoded to the local container,
  so it can never reach Supabase. Hitting Supabase requires typing `--env supabase`.
- `atlas migrate lint` requires a (free) `atlas login` as of Atlas v0.38.
